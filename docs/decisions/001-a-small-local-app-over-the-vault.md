# 001 — The board is a small local web app that reads brand notes from the vault and writes images and Moodboard blocks into it

> **Summary.** A separate local web app, with its own repository, shows a brand's notes as read-only text next to a grid of its images, and takes new items by paste: a brand, a screenshot, an optional page address and a one-line description. It reads and writes the vault only as workflow ADR 018 fixes, through a small local API that the page and a later browser extension both call. It costs one more app to run and a dependency for thumbnails.

Accepted by the owner on 2026-10-15: decisions 1 to 11, including Python with Pillow and a standard-library server; the items under "Open" stay open for later slices.

## Context

The owner documents brands, personal and client, in the vault that Sympose reads, and wants a visual surface for the part that is images: screenshots of inspiration, with a note of what each is for. Workflow ADR 018 (accepted 2026-10-15) fixed what the vault holds: `Brands/<slug>/` notes, a `<slug> - Moodboard.md` note whose blocks are an optional embed line, a description and an optional `[source](url)` line, and a gitignored `Board/<slug>/` folder with image files and `thumbs/`. This record fixes the app. What was settled in chat the same day:

- It is a separate app, not a feature of Sympose, which is a vault companion that reads notes.
- All text on screen comes from the notes; the app does not render Markdown, it shows the text.
- The input is a paste: pick a brand from a list, paste a screenshot (a clipboard image), optionally paste a page address, type a short description, press Enter.
- A browser extension that sends the page address (and later the picture) is the likely second input, so the code is built toward it.
- It stays small; a headless browser for automatic page captures would outweigh the rest of the project.
- The workflow's rules apply: the repository may be public, so no real brand, client or vault path appears in it; a model never writes a claim into a note.

## Decision

1. **Shape.** A local web server and one page. The server binds to `127.0.0.1` only and refuses a request whose `Origin` is not its own page (or, later, the extension's). The page is the first client of the server's API; the extension would be the second, so nothing is done in the page that the API cannot do.
2. **Where the vault is.** The vault path is an argument or environment variable and is never written into the code or the repository.
3. **What is read.** The brand list is the folder names under `Brands/`. For a brand: the hub note's frontmatter (`status`, `client`) as badges, the first paragraph of the hub body as the summary line, and every other `<slug> - <Title>.md` as a text panel titled by the part after ` - `, in a fixed order for `Positioning`, `Voice`, `Visual identity`, `Rejected ideas` and `Moodboard`, then the rest alphabetically. A note is shown by removing the frontmatter, keeping line breaks and turning `[[a|b]]` into `b` and `[[a]]` into `a`; the API returns this as plain text and the page shows it as text, which React escapes (see the amendment on plain text below). A new note title needs no change to the app.
4. **The grid.** It is built from the brand's Moodboard blocks, newest first, in a layout that keeps each image's own proportions (no cropping to a common ratio). Thumbnails are shown; the original opens on click.
5. **Adding an item.** One input box takes a pasted image or a pasted address, in either order, and a one-line description; Enter adds the item. The description and the address are optional. A brand is always chosen (the last one is remembered), or the item goes to `_unsorted`. Dropping image files onto the page does the same as pasting them, through the same API call and the same checks (decision 6). While taking several screenshots from one site, a switch keeps the last address for the next item.
6. **Images.** The original is stored as pasted, unchanged. A thumbnail about 640 pixels wide is made at the same time and kept in `thumbs/`; it can be rebuilt from the original. The server accepts only PNG, JPEG, WebP and GIF, checked by the file's first bytes and not its name, and refuses a file over 25 MB.
7. **An address with no picture.** The server tries once to fetch the page's title and preview image and keeps what it gets; a failure is silent and the item stays a bare link. The app never takes a screenshot of a page by itself.
8. **What it writes.** Only `Board/<slug>/` and the end of the brand's Moodboard note, in the block format of workflow ADR 018; never any other note, and never an edit to a block. Deleting an item removes its block and its files together, and may remove any block the page shows, including one written by hand, because the format has no marker that tells the app's own text from yours; it needs the owner's explicit click on that block, and it is refused if the block's text has changed since the page showed it (the key is a hash of the block's exact text; the embed's image id names the files). A block edited by hand in Sympose or Obsidian is shown as it stands.
9. **Not in the first version.** Editing note text in the app, copying descriptions anywhere else, a search, the extension, and automatic page capture. Also an Assets section for a brand's own logos and icons, including SVG: it needs its own record, because an SVG can carry script (shown only through `<img>`, served with `nosniff` and a sandbox policy), because it holds the brand's own deliverables apart from inspiration, because workflow ADR 018 says the vault holds no client assets (it would need an amendment saying `Board/` is local and never pushed), and because a copy here can drift from the master file. Small SVG source inline in a note is allowed by the owner for their own logos and icons, but no app in the owner's setup draws it from a note (Sympose does not; Obsidian does).
10. **Tests** cover the block reader and writer on synthetic text (a block, one with no image, one with no address, one with extra lines), the refusals in decision 6, and the origin check; each rule is checked against a weakened version with `scripts/mutate.py` once there is code.
11. **Language and dependencies.** Python, with a minimal server built on the standard library (`http.server`) and no Python web framework. The page is a React app served by that server, which it calls through the API ([ADR 002](002-the-page-is-a-react-single-page-app.md)). Pillow is the one third-party dependency, used only to make thumbnails (decision 6) and to read an image's size; it is pinned in a requirements file added with the first code. On the Python side anything beyond it needs its own record (`docs/CODE_QUALITY_STANDARDS.md`, section 0); the page's npm dependencies are fixed by ADR 002. The owner chose this on 2026-10-15, taking the recommendation: "Python with Pillow and a minimal stdlib server". The reason behind it is that the vault's own scripts are Python, so the block reader and writer, the gates and the mutation check all run in one language, and the standard library already covers the server, the file handling and the tests.

## Consequences

The owner can drop a screenshot and a thought into a brand in a few keystrokes, and the text is searchable in Sympose because it lives in a note. The images stay out of git, as ADR 018 intends. Because the page uses only the API, the extension is a new client and not a rework.

The cost is that a local server that writes files is a target for any page in the browser, so the origin check and the loopback binding are part of the design and need their own tests. Thumbnails need an image library, which the standard library does not provide. `Board/` has no history or remote, so its backup is the owner's to arrange. A description written for a client brand reaches the private remote through the Moodboard note, as ADR 018 says.

Open: the Assets section (decision 9); how Pillow is installed (a virtual environment is likely; decision 11 fixes the language and the library, not this; the minimum Python version is fixed in the amendment on plain text below); where the server's own settings live; whether Sympose renders `![[…png]]` in the Moodboard (an open question in the workflow's SPEC); how the extension is allowed through the origin check; a backup for `Board/`.

## Alternatives rejected

- **A feature inside Sympose.** One app to run and the vault path already known, but Sympose is a vault companion that reads notes, and a media board would inherit its constraints (it refuses paths outside the vault). Would be right if the board needed Sympose's search or its persona.
- **Automatic screenshots of a pasted address.** Saves the owner's own screenshot, but needs a headless browser, and the results are often cookie banners or login walls; the owner's crop is the point. Would be right as an optional button if the pasted-image flow proves too slow.
- **A bookmarklet as the second input.** Cheap, but sites with a strict content policy block it and Safari is stricter about reaching `localhost`. Would be right if the extension proved too heavy and the owner's browser allowed it.
- **Resizing in the browser page.** No server dependency, but the extension would have to do it again. Would be right if the page stayed the only client.
- **Shrinking the original on paste.** Saves disk, but cannot be undone; a screenshot cannot be retaken. Would be right if disk use grew past what the owner wants to keep, as a separate, explicit step.
- **A JavaScript stack (Node, with or without a UI framework).** Would match the UI of Stylo and Sympose, and the page is JavaScript anyway. But the vault scripts, gates and mutation check are Python, so the block logic would need a second toolchain and a second set of tests; Node's standard library has no image resizing, so thumbnails would bring in a native package (for example `sharp`) that is heavier than Pillow, and a framework would add more. Would be right if the app were to share code with Stylo or Sympose, or if the page grew into a real application.
- **A Python web framework (Flask, FastAPI or similar).** Routing and request parsing are less code to write. But each adds a dependency tree to cover what `http.server` already does for about five routes on one loopback address, and the origin check and the size limit (decisions 1 and 6) are code we write and test either way. Would be right if the API grew past a handful of routes, or if the standard-library server proved unsafe or too slow under real use.
- **Thumbnails with macOS `sips`, no Pillow.** Zero Python dependencies, but it shells out to a tool that exists only on macOS, handles file formats differently, and is harder to test with generated images. Would be right if the app were macOS-only for good and the one dependency became a burden.
- **A native Swift app.** A good fit for the Mac and for pasting from the clipboard, but it cannot share the API with a browser extension, and none of the vault tooling is Swift. Would be right if the owner wanted a menu-bar app and dropped the extension.
- **Cropping thumbnails to a fixed ratio.** A tidy grid, but the owner already chose the crop that matters. Would be right if the grid were only an index.

## Amendment (2026-10-15): the page is a React app

The owner chose React for the page, expecting the app to grow ([ADR 002](002-the-page-is-a-react-single-page-app.md)). Decision 11 is edited to say so; the server, the API and Pillow are unchanged. The "JavaScript stack" alternative above stays rejected for the server and for the vault code; only the page changes.

## Amendment (2026-10-15): what delete may remove

Decision 8 said the app never touches a block it did not write. The Moodboard format (workflow ADR 018, decision 5) has no marker, so for a block with no image the app cannot know who wrote it, and a marker would put text of the app's own into a note. The owner decided, in chat the same day: delete may remove any block the page shows, only after an explicit click and only if its text is unchanged since it was shown. Decision 8 is edited to say so and its "how a block is found again" question is closed. The key is a hash of the block's exact text for every block, image or not, so that an edited block is refused whatever it holds; the image id names the files to remove with it, and a block whose embed is not an id this app made removes no files. Adding is unchanged: the app only appends. A delete rewrites the note through a hidden temporary file beside it (`.board-<random>.tmp`), renamed over the note or removed if anything fails, so that a crash cannot leave half a note; this is the only write besides the two named in decision 8. A heading and the lines under it up to the next blank line are not an item, so an item typed directly under a heading is hidden with it. Workflow ADR 018, decision 6, lists only appending under the Moodboard, so it needs a matching amendment in the workflow repository, which is the owner's to approve.

## Amendment (2026-10-15): plain text from the API, and Python 3.11 as the minimum

Two details of the read side, decided by the owner in chat the same day. First, decision 3 said the app escapes the HTML of a note before showing it. The page is a React app ([ADR 002](002-the-page-is-a-react-single-page-app.md)), and React escapes any text it is given, so the API returns a note's text as plain text and the page shows it as text; an escaping server would make the page show `&amp;` literally, and a second client (the extension) would have to undo it. The page must therefore never put a note's text into the page as HTML (no `dangerouslySetInnerHTML`). Second, the minimum Python version is 3.11: 3.10 reaches end of life this month, so 3.11 is the oldest release worth supporting, and a floor below the owner's own interpreter (3.14) keeps the code from drifting onto features only the newest one has. The server's entry point checks it when it is written (slice 3).

## Amendment (2026-10-15): the API's shape, and how Pillow is installed (slice 3a)

What slice 3a fixed. The owner chose in chat: the API refuses to add to a brand that has no Moodboard note and creates none, so the app writes no text of its own into a note; and slice 3 is split into the API (3a) and the page (3b). The rest is the implementer's choice, to be confirmed on review.

- **JSON, not a form upload.** An item is added with `POST /api/brands/<slug>/items` and a JSON body `{description, source, image}`, the image as base64 text (a 25 MB image is about 34 MB of text, on the loopback). The standard library no longer parses multipart forms, and a JSON body is the same for the page and for the extension. A body that is not `application/json` is refused, so a form on another site cannot send one. The routes are listed at the top of `board/server.py`.
- **The origin check, completed.** Every request must name this server in `Host` (`127.0.0.1:<port>` or `localhost:<port>`), which stops a web page reaching the server through a DNS name that points to it. A request that changes anything must carry an `Origin` that is the server's own; a request with any other `Origin` is refused, whatever its method. The server sends no CORS header. How the extension and the dev server are let through is still open (ADR 002).
- **Delete** is `DELETE /api/brands/<slug>/items/<key>` with the block's hash as the key (decision 8).
- **Pillow** is installed into a virtual environment, `.venv/` (not committed), from `requirements.txt` with the version pinned; the tests gate runs from it. The pinned version is the latest at the time (12.3.0).
- **Not in 3a:** the address-only fetch of a page title and preview (decision 7), which needs its own care about what the server may fetch; the `_unsorted` brand (decision 5), which has no Moodboard note to write to; the page.

## Amendment (2026-10-16): a delete whose files stayed is a 200 with a warning

The first API answered 500 when a delete removed the block from the note but could not remove its image files, so the page re-read the brand after every delete attempt and told the owner "N of M deleted" a little wrong in that case: the item was gone. The owner agreed in chat the same day ("do all", after the assistant recommended this change). Now `DELETE /api/brands/<slug>/items/<key>` answers 200 with `{"deleted": "<key>", "warning": "<plain text>"}` when the block went and the files stayed; the text holds no path. A key that matches nothing, a changed block and the other refusals keep their statuses, and 500 is left for what is unexpected. The page counts such an item as deleted and keeps a message up in the confirmation, with a Close button, until the owner closes it. What this does not change: the order (block first, files second), the rule that nothing else is written, and the files that stay are still the owner's to remove by hand in `Board/<slug>/`. The record was written after the code in this one case; the assistant should have written it first (`docs/sop/write-an-adr.md`).

## Amendment (2026-10-20): one narrow exception to "never an edit to a block"

Decision 8 says the app never edits a block. [ADR 009](009-special-cards-for-colours-text-and-type.md) makes one exception, asked for by the owner on 2026-10-20 ("edit button to edit the hex value"): the owner's click on the pencil of a colours, text or type card replaces that block by a card of the same kind, only if the block's text is unchanged since shown (the same key check as a delete) and only through the temporary-file rename a delete uses. No other block, image block, line of words or note is ever edited. The rest of decision 8 stands.

## Amendment (2026-10-20): an item may be moved to another place in the Moodboard

Decision 8 says the app only appends, edits a card in place (amendment above) and deletes. The owner asked on 2026-10-20 for the cards to be draggable, "so that the user can re position the cards the way the user wants it", and asked where the order lives. It lives in the Moodboard note and nowhere else: the page shows the note's blocks last to first, so the order of the file is the order of the grid. The owner chose, in chat the same day, to keep it that way and to have a drag rewrite the note ("Option 1: move the block in the Moodboard note"), over a second file in `Board/<slug>/`, which would have been a second source of truth that goes wrong when a block is edited by hand or a card is edited (the key is a hash of the text).

1. **What is written.** One item's lines move to just before another item's lines, or to the end of the note. The block's text is not changed by a single byte, so its key stays the same; everything else in the note is kept byte for byte, as in a delete or a card's edit. The note is rewritten through the same hidden temporary file and rename (workflow ADR 018's amendment of 2026-10-16, decision 5), under the same lock, and refused if the note changed meanwhile (409, nothing written, try again).
2. **What may move.** Any item the page shows, a card of ADR 009 or not, for the same reason a delete may remove any: the format has no marker of who wrote a block. It must be unchanged since shown, and a text that two blocks share is refused, as in a delete. A heading block, the frontmatter and every other note are never moved; the page's other cards (the hub and the notes) cannot be dragged and keep the place their date gives them (ADR 002, amendment on the cards), so after a move a note can sit between other items than before.
3. **The API.** `POST /api/brands/<slug>/items/<key>/move` with `{"before": "<key>"}` or `{"before": null}`. The words are the note's, not the page's: the block goes just before the block with that key, or to the end of the note when it is null (the page shows the end of the note first, so the card at the top of the grid is the last block). A move that leaves the order as it is writes nothing and still answers 200. Nothing but `before` may be in the body (400); a block moved before itself is refused (422); a key that matches nothing now, or two identical blocks, is 409. The answer is `{"moved": "<key>"}`; the page reads the brand again.
4. **The page.** A grip button on an item card, shown and sized like the trash button, is the only thing that starts a drag, so a click on a picture, a link or the words and a drag of selected text are as they were. A card is dropped above or below another item card, the half of the card the pointer is in; the hub, the notes and the box that adds an item take no drop. The grip also works from the keyboard: Up and Down arrow keys move the card past the item before or after it, and the focus stays on the grip. The drag is the browser's own (HTML drag and drop), so no dependency is added. It is checked with a mouse in a real browser; on a touch screen the browser's long-press drag is expected to work and has not been tried, and the arrow keys have no touch equivalent yet.
5. **Dates.** An item with no image of the app's own takes the date of the block before it in the note (API, items), so moving such an item changes the date the page gives it, and the place its notes take in the grid follows. The note is not touched by this: dates are worked out when it is read.

What this does not change: nothing else is written, no model writes text into a note, and the write is the owner's own act (the drop, or a key press on the grip). The text for workflow ADR 018 is in the handoff for the owner to apply; until it is, `docs/reference/VAULT_LAYOUT.md` records the exception.

## Amendment (2026-10-20): a block that shares its text with another is told apart by a copy number

Decision 8's key is a hash of a block's exact text, and a delete, a card's edit or a move of a text that two blocks share was refused ("remove the extra copies by hand first"). The owner hit it with three blocks of the same words ("I can't click delete") and chose, in chat the same day, that the clicked copy is the one that is acted on, over a delete that takes any copy or keeping the refusal.

1. **The key names the copy.** In the brand view an item's `key` is still the hash of its text when no other block has that text. When another does, it is `<hash>-<copy>`, the copy counted from 0 in the note's order (the page shows the note last to first, so the first card of a set of twins carries the highest number). The routes of ADR 001 and 009 take either form wherever they take a key, `before` of a move included.
2. **What is checked.** A key with a copy number is refused (409, as a block that changed since it was shown) when the note has no such copy any more. It does not say how many copies there were when the page showed them: the copies are the same text, so the only thing the number settles is which of them is meant, and a copy deleted by hand meanwhile is the case it cannot tell from the page's own. A bare hash that two blocks share is still refused (409), so a client that does not know the numbers is as safe as before.
3. **Picked copies.** The page deletes picked cards one after the other, first card first, which for copies is the highest number first, so the numbers of the copies still to go stay good. A repeat of a text is no longer numbered by the page: the server's keys are already one to a block.
4. **What does not change.** Nothing about what is written: a delete removes one block and, if no other block names them, its files; a move changes a block's place only. A lookup is kept by the address, so it still serves every copy.
